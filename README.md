# Silica Store

The default catalog for the **Silica** Minecraft mod's in-game Store.

Silica puts programmable computers in Minecraft, scripted in modern JavaScript. This repository holds
scripts and apps for them. A player opens the **Store** app on a SilicaOS desktop, browses what is here,
and installs an entry — which lands as ordinary, editable source files in their own scripts folder.

Everything in this repository is MIT-licensed, so a copy you install is genuinely yours to edit.

## How a server uses this catalog

The Store reads a list of repositories from the server config, `silica-server.toml`:

```toml
[store]
    enabled = true
    repos = ["Mr-Benedict/silica-store"]
```

Each entry in `repos` is `owner/repo` or `owner/repo@ref`, where `ref` is a branch or a tag. **The ref
defaults to `main`.** So `"Mr-Benedict/silica-store"` tracks this repository's `main` branch, and
`"Mr-Benedict/silica-store@catalog-v1"` would pin it to a tag.

A reference is never a URL. There is no host, scheme or port to configure: the mod serves every catalog
from `raw.githubusercontent.com` and nothing else. An admin who pastes a URL gets a parse error, not a
request.

**This is not a Silica-only catalog.** Any public repository laid out the way this one is works as a
store, so a pack author or a server admin can publish their own and add it to `repos` alongside — or
instead of — this one.

### What the mod actually fetches

Two things, and only on a player's explicit action:

1. **`index.json`** at the repository root, when someone opens the Store or presses Refresh. It is
   cached server-side per repo+ref for a few minutes, so browsing is normally instant and silent.
2. **The files of an entry a player installs**, plus that entry's `README.md` when they open its listing.

Nothing is fetched on server start, on world load, or on a timer. A server nobody touches never contacts
GitHub at all. Scripts running inside Silica cannot reach the network themselves — the catalog fetch is
the mod's, made for the operating system, never reachable from sandboxed code.

## The folder contract

```
README.md · CONTRIBUTING.md · LICENSE
index.json                          ← generated by CI. Never edit by hand.
scripts/
  <entry-id>/
    silica.json                     ← the entry's metadata (required)
    README.md                       ← required; rendered in the Store app
    <entry-id>.js                   ← kind: "script"
    entrypoint.js + ui/             ← kind: "app"
tools/build-index.mjs               ← the validator and index generator
.github/workflows/catalog.yml
```

One folder per entry, and the folder name **is** the entry id. Nothing else lives in `scripts/`.

- **`kind: "script"`** is a plain terminal script: exactly one `.js` file at the entry root, and no `ui/`
  directory. It installs as `<entry-id>.js` in the player's scripts folder.
- **`kind: "app"`** is a SilicaOS app with a real HTML/CSS/JS interface: an `entrypoint.js` (or an
  `index.html`) at the entry root, plus whatever else it needs. It installs as the folder `<entry-id>/`.

Structural limits, all enforced by CI and again by the mod (each is a server knob, shown here with its
default):

| limit | default | knob |
|---|---|---|
| one installable file | 262144 bytes | `[store] maxFileBytes` |
| installable files in one entry | 64 | `[store] maxEntryFiles` |
| a rendered `README.md` | 131072 bytes | `[store] maxReadmeBytes` |
| entry-relative path length | 160 characters | — |
| entry-relative path segments | 6 | — |

No symlinks. No dotfiles or dot-directories, anywhere. No `..` in any path.

## `scripts/<entry-id>/silica.json`

```json
{
  "id": "stock-display",
  "title": "Stock Display",
  "summary": "What is in any inventory on the Silica network, by name",
  "kind": "app",
  "category": "storage",
  "author": "Silica",
  "needs": {
    "doors": ["gfx", "network"],
    "parts": ["gpu", "nic"],
    "mods": ["refinedstorage"]
  },
  "minSilica": "0.1.0"
}
```

| field | required | what it is |
|---|---|---|
| `id` | yes | must equal the folder name; `[a-z0-9-]`, 1–48 characters |
| `title` | yes | the name shown in the Store list |
| `summary` | yes | one line, no newlines, at most 160 characters |
| `kind` | yes | `script` or `app` |
| `category` | yes | one of the ten below |
| `author` | yes | who wrote it. First-party entries use `Silica` |
| `needs.doors` | no | the capability doors the code touches |
| `needs.parts` | no | the computer parts a player must actually have installed |
| `needs.mods` | no | mod ids the entry needs to be useful at all |
| `minSilica` | no | the earliest Silica version it is known to work on |

**Categories** — exactly these, and CI rejects anything else:
`starter` · `example` · `redstone` · `storage` · `energy` · `security` · `automation` · `monitoring` ·
`mining` · `other`

### `needs`, precisely

**`doors`** are Silica's server-wide capability doors. There are thirteen:

| door | what it gates |
|---|---|
| `redstone` | driving and reading redstone on the computer's own faces |
| `gfx` | the terminal canvas / display list (needs a GPU) |
| `fs` | the computer's saved filesystem (needs a hard drive) |
| `network` | wired blocks and other computers (needs a NIC) |
| `pads` | bound pads and pocket computers |
| `web` | a real HTML/CSS/JS interface — added by the optional `web-display` jar |
| `detector` · `ejector` · `turret` · `spawn` · `security` · `geo` | the matching peripheral's own verbs |
| `multidimensional` | reaching a network that crosses dimensions |

List **every door the code may call**, whether or not it can manage without it — this is the list the
Store shows a player before they install, so it should read as *"this script wants to drive redstone and
talk to the network"*. A Path-B app with an HTML interface uses **`web`**, not `gfx`; `gfx` is the
terminal canvas, which is a different surface.

A peripheral door gates only that peripheral's *own verbs*. Reading an inventory is generic, so a script
that lists what is inside a Collector needs `network` and no peripheral door — which is why the
`collector` entry declares none, and says so in its own header.

**`parts`** are the computer parts a player must genuinely have for the entry to do its job: `gpu` (opens
`gfx`), `hdd` (opens `fs`), `nic` (opens `network`). This is a shorter list than `doors` on purpose — a
script that draws an optional screen card but works fine without a GPU touches the `gfx` door and does
**not** require the `gpu` part. Redstone needs no part at all.

**`mods`** names a foreign mod the entry reads through one of Silica's optional integration jars — for
example `mekanism`, `refinedstorage`, `rftoolsbuilder`, `rftoolspower`. Omit the key entirely when there
is none.

`needs` is **disclosure, not enforcement.** Silica's capability doors are server-wide settings, not
per-app grants: a declared door is information a player uses to decide, and the confirm dialog they see is
not a sandbox boundary. What actually protects a server is the JavaScript sandbox, those server-wide
doors, and the fact that a human chose to install this.

## `index.json`

The one file the mod fetches to build a whole catalog. It is every `silica.json` concatenated, plus the
file list, sizes and hashes that CI computed:

```json
{
  "version": 1,
  "name": "Silica Store",
  "generated": "2026-07-29T20:00:00Z",
  "entries": [
    {
      "id": "counter",
      "title": "Counter",
      "summary": "…", "kind": "app", "category": "example", "author": "Silica",
      "needs": { "doors": ["web"], "parts": ["gpu"] },
      "readme": "scripts/counter/README.md",
      "digest": "d6e2e94dcd80a5c96863fac0d8e18b4aeeb82737271c9333a0e35b5f4d04a1c2",
      "files": [
        { "path": "entrypoint.js", "sha256": "…", "bytes": 2118 },
        { "path": "ui/index.html", "sha256": "…", "bytes": 1204 }
      ]
    }
  ]
}
```

`files[].path` is **entry-relative**, with forward slashes, sorted. `silica.json` and the entry-root
`README.md` are catalog metadata and are not in it — they are never installed.

`digest` is the entry's identity: one hash over all of its installable files, so a multi-file app is one
thing to compare rather than five. The mod recomputes it over what is on the player's disk to tell
*installed and up to date* from *upstream has changed* from *you have edited this*. Its exact definition —
it is a cross-language contract — is in the header comment of
[`tools/build-index.mjs`](tools/build-index.mjs).

**Do not edit `index.json`.** CI regenerates it from the folder tree when a pull request merges, and
commits it back.

## The tool

```
node tools/build-index.mjs --check     # validate; prints every problem, exits non-zero if any
node tools/build-index.mjs --write     # validate, then write index.json
```

Node 20 or newer, standard library only. There is nothing to install.

## Writing a script or app with an AI

[**AI-GUIDE.md**](AI-GUIDE.md) is a complete, self-contained technical briefing on the Silica script API —
the execution model, every global and peripheral verb, the capability doors, the events, the Path-B bridge,
and two known-good worked examples. Paste that one file into Claude, ChatGPT or anything similar, say what
you want the script to do, and it has everything it needs to write one that runs. It is written for a model,
not for a human, so it is dense on purpose.
